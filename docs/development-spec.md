## 1. 产品范围与交付边界

### 1.1 不可改变的原则

1. 内容准确性高于开发进度和内容数量。只发布有权威来源、版本和审核记录的内容。
2. 法条原文只取国家法律法规数据库；其他官方来源按 PRD 用于案例、解释及修订跟踪，不能替代原文基线。
3. 法条层、解读层、案例与题目层分别建模，每条解读、每张卡和每道题至少引用一条具体版本的法条。
4. 内容内置、答案确定；无账号、无 UGC、无社区、无 AI 问答、无法律咨询和个案处理建议。
5. 无内容服务器、无远程配置、无遥测/广告/崩溃上报 SDK、无运行时内容下载。联网不是核心功能的前提。
6. 用户状态只在本机保存，不启用 CloudKit 或自建同步。系统备份不等于 App 自行同步，也不作为 V1.0 功能承诺。
7. 读者可在无网络时完成浏览、检索、测验、收藏、朗读、生成分享图及纠错草稿。打开官方网页、发送邮件、向第三方分享由用户主动交给系统或外部 App，实际发送不属于离线保证。

### 1.2 V1.0 功能覆盖

| ID | 功能 | V1.0 必须交付 | 验收重点 |
|---|---|---|---|
| F01 | 首启与免责 | 未勾选“已知悉”不可进入；记录声明版本和知悉时间 | 重启不重复弹出同版本；声明升级后重新知悉 |
| F02 | 首页 | 今日一题、继续学习、内置推荐场景 | 无网络和无学习历史都有完整页面 |
| F03 | 学法堂 | 主题树、知识卡、学习路径 | PRD ★ 主题都有内容；刑法/民法为主篇，治安法为补充篇 |
| F04 | 知识卡 | 结论、故事、拆解、法条、误区、小测验、来源、免责、纠错 | 全部引用可跳转；不把情境示例包装为真实裁判 |
| F05 | 查法条 | 三法现行全文、关键词检索、条号直达、拼音联想 | 不截断官方原文；同条号跨法律返回选择列表 |
| F06 | 法条详情 | 官方原文、版本状态、更新至月份、复制、关联卡 | 原文与包内文本一致；没有解读时明确说明 |
| F07 | 每日一题 | 本地确定性选题、答题解析、可选本地通知 | 同一天重复进入是同一题；拒绝通知不影响答题 |
| F08 | 闯关与称号 | 青铜→白银→黄金→王者，关卡解锁与结算 | 重复提交不重复计分；退出重进可恢复 |
| F09 | 错题本 | 自动收录、筛选待复习、一键复习、回到知识卡 | 答错即关联题目、卡片及法条；历史不因复习消失 |
| F10 | 我的与收藏 | 法条/卡片收藏、学习记录、连续打卡、称号 | 重启保留；内容升版后无静默错配 |
| F11 | 朗读 | 法条及知识卡朗读、暂停/继续/停止、语速设置 | 使用系统 TTS；离线可用语音不足时清楚降级 |
| F12 | 分享 | 本地生成法律知识分享图并调起系统分享 | 包含 App 名、原文、条号、版本、官方来源和免责声明 |
| F13 | 设置与纠错 | 字号、朗读、提醒、隐私说明、免责、邮件草稿 | 未配置邮件客户端可复制内容 ID 与反馈文本 |

数量门槛：可发布知识卡至少 100 张，其中刑法不少于 40、民法不少于 45、治安法不少于 15；可发布题目至少 300 道，每题关联至少一张卡。用 `primaryLawId` 唯一计入卡片分布，跨法引用不得重复计数。至少每张卡有一道关联题。数量达标不能覆盖任何准确性门禁。

V1.0 不包括视频课程、付费/订阅、好友排行、账号、同步、在线咨询、文书生成、案件评估、远程内容下发。Android 本次只建立目录和边界，不能算入 V1.0 完成度。

│       └── releases/<packageId>/   # 已审核、冻结的完整内容包

这是目标布局。本次只提交 spec、架构产物、开发约束和目录说明；尚未创建的工程、工具、schema、内容与测试须由后续需求实现，不提交空壳工程冒充可运行应用。

- `ios/` 和 `android/` 各自拥有构建、依赖锁定、包标识、测试、签名和发布流程。任意一端构建不得安装或执行另一端工具链。
- 不建立跨平台 UI/业务代码模块，不把 Swift/Kotlin 实现放入 `resource/`。共享的是原始素材、内容契约及语言无关的行为测试样例。
- 共享资源由平台构建步骤显式复制或转换成只读 Bundle/assets；运行时不得读取仓库相对路径，也不得写回 `resource/`。
- 图标母版、版权/授权说明、作者、来源、用途和允许修改范围随资源保存。iOS Asset Catalog、Android density/adaptive icon 等平台产物归各端；规定生成命令，禁止独立手工修改生成副本。
- 每个平台声明使用的 `packageId` 和文件摘要。资源改变必须标记受影响平台并通过共享内容门禁；Android 启动后，公共 schema 的破坏性变更须两端兼容评估。
- 构建缓存、签名密钥、个人配置、DerivedData、Gradle 缓存、真实用户数据及 worktree 目录不提交。

## 3. 目标架构与技术决策

交互式架构图：[识法目标架构](architecture/lawsense-architecture.html)；可编辑源文件：[Archify JSON](architecture/lawsense-architecture.json)。图表示设计目标，不代表现有代码结构；服务均位于设备内，图中的审核管线位于开发侧。

### 3.1 方案与理由

| 决策 | 选择 | 理由与边界 |
|---|---|---|
| iOS 界面 | SwiftUI + Observation，iOS 17+ | 与 PRD 一致；按功能组织，默认 MV，不为每屏添加转发式 ViewModel |
| 业务逻辑 | 值类型 + 纯函数；少量有状态的功能模型 | 选题、判题、等级、检索排序可脱离 UI 测试 |
| 官方内容 | 版本化 UTF-8 JSON，应用包只读 | 与用户状态分离；有摘要、引用和专业审核证据 |
| 用户数据 | SwiftData + 明确 schema 版本/迁移计划 | 存收藏、练习、进度及设置；不复制整套官方文本 |
| 本地检索 | 构建时生成确定性倒排索引 | 支持中文词组/字符组合与拼音词典；避免每次查询遍历全文 |
| 平台能力 | 原生 TTS、本地通知、系统分享/邮件 | 无专有服务依赖；通过小型适配器替换测试 |
| Android | 独立原生工程，技术栈待 V2 决策 | 复用内容和验收契约；本次不锁定 SDK、Gradle 或第三方库版本 |
| 网络 | 核心不建网络层 | 官方来源打开/邮件发送由用户触发系统能力 |

SwiftUI 的 Observation 可用于 iOS 17+；采用该能力而不提高最低系统版本。参见 [Apple：管理模型数据](https://developer.apple.com/documentation/SwiftUI/Managing-model-data-in-your-app)。用户库通过 `ModelContainer` 管理存储和迁移，参见 [Apple：ModelContainer](https://developer.apple.com/documentation/swiftdata/modelcontainer)。具体工具链在 iOS 初始化需求中锁定并记录，不以 skill 中较新系统示例替代 iOS 17 的可用性检查。

### 3.2 iOS 逻辑组织（先用目录，不提前拆大量 Package）

| 目录/职责 | 输入与输出 | 状态及依赖 |
|---|---|---|
| `App/` | 启动、依赖装配、首启门禁、路由 | 创建内容库、用户库及适配器；唯一组合入口 |
| `Features/Home, Learn, Laws, Practice, Profile/` | 用户操作 → 展示状态/命令 | 视图绑定局部模型；不直接解析 JSON 或遍历法律全文 |
| `Domain/` | 领域值对象、选题、判题、关卡、打卡 | 不依赖 SwiftUI、SwiftData 或系统通知 API |
| `Data/Content/` | 只读内容、反向引用、搜索索引 | `ContentRepository`/`SearchService`；返回值类型或稳定 ID |
| `Data/User/` | 持久化记录和迁移 | `UserDataStore` 单一写入者，显式提交 |
| `Services/` | 朗读、提醒、分享、反馈草稿 | 系统副作用隔离；每项按需要建立最小接口 |
| `DesignSystem/` | 颜色、字体、卡片、版本/来源/免责组件 | 语义 token；不含内容事实或业务判断 |

依赖方向：页面及功能模型使用领域类型、内容查询和用户存储接口；持久化/系统适配器实现接口；App 入口负责注入。没有真实替换或测试需求时不增加通用 Repository 基类、UseCase 包装或大型状态框架。

### 3.3 状态、并发与导航所有权

- UI 状态由对应功能的 `@MainActor @Observable` 模型拥有；短暂的展示/焦点状态留在 View。
- 用户库所有写操作进入一个受串行隔离的 `UserDataStore`（采用 `@ModelActor` 或等效单一 actor 实现），SwiftData 实例不跨 actor 传递；UI 收到不可变快照或 ID。数据保存成功后再确认完成，失败显示可重试错误。
- 内容解析/搜索不阻塞主线程；读入边界完成校验，内部使用可信类型。取消旧查询并用请求标识保证晚到结果不能覆盖新关键词。
- 每个 Tab 有独立导航栈。iPad 常规宽度采用列表/详情分栏，紧凑宽度回落为导航栈。详情路由持有类型化 `ArticleRef`/`CardID`/`QuestionID`，不靠标题定位。
- 通知点击先经过免责与内容就绪门禁，再交给统一内部路由；无法解析的 ID 显示“内容已更新”并提供目录入口。
- 复杂答题流使用显式状态转换；其余页面维持简单 MV。需要升级架构时记录具体压力与迁移路径。

## 4. 领域词汇与共享内容契约

### 4.1 身份、版本与时间

| 词汇 | 语义 |
|---|---|
| `LawID` | 法律稳定 ID：`criminal`、`civil`、`public_security`；不随名称展示变化 |
| `LawVersionID` | 官方法律版本身份，关联颁布/施行日期；例如 PRD 的 `zaf_20260101` 仅为预期基线标识 |
| `EditionID` | 某法律版本的一次已校对录入版；冻结后不可覆写，纠正录入错误也生成新 edition |
| `ArticleRef` | `{ lawId, lawVersionId, editionId, articleKey }`，精确定位当时引用的原文 |
| `articleKey` | 如 `264`、`133-1`；支持“第…条之一”，不能只用整数 |
| `CardID` / `QuestionID` | 稳定、不复用的实体 ID；内容变更另加 `revision` |
| `packageId` | 一次完整内容发布身份，如 `content-2026-10-r1`；不等同 App 版本或 JSON schema 版本 |
| `schemaVersion` | 内容格式兼容版本；客户端不支持则拒绝读取，不能猜测字段 |
| `reviewedAt` | 真实完成复核的日期；“更新至 YYYY-MM”据此展示，不能用打包时间冒充 |
| `LocalDay` | 公历本地日期键 `YYYY-MM-DD`；记录事件的 UTC 时间与当时时区 ID，不能用 24 小时秒差计算连续天 |

所有 ID 使用可稳定序列化的字符串，无随机展示标题生成 ID。`articleKey` 的数值部分和增补序号分别参与排序。条文内部“款/项”另存可选定位，不通过自由文本拼接伪造引用。

### 4.2 发布包文件与字段要求

以下是必须实现的逻辑契约。M1 将其落成 `resource/content/schema/` 下的 JSON Schema 和合法/非法样例；本 spec 不宣称这些文件已实现。

| 对象/文件 | 最少字段及约束 |
|---|---|
| `manifest.json` | `schemaVersion`、`packageId`、`createdAt`、`minReaderVersion`（内容读取器版本）、`lawEditions[]`、`files[]`、`releaseApprovalId`；每个文件有相对路径、SHA-256、字节数；禁止绝对路径和 `..` |
| `lawEditions[]` | `lawId`、`lawVersionId`、`editionId`、`name`、`promulgatedAt`、`effectiveAt`、`statusAtReview`、`reviewedAt`、`sourceId`、`articleCount`、`articleInventoryHash`；现行性是复核时状态，不声称实时更新 |
| `laws/<editionId>.json` | 有序 `articles[]`；每条含 `articleKey`、`displayNumber`、`chapterPath[]`、`order`、`originalText`、`textHash`、`reviewedAt`、`sourceId`；原文含完整条号及正文 |
| `sources.json` | `id`、`kind`、`publisher`、`title`、`url`、`publishedAt`（来源可确认时）、`retrievedAt`、`snapshotHash`；明确区分法条、案例、司法解释/官方解读来源 |
| `interpretations.json` | `id`、`revision`、`points[]`、`misconceptions[]`、`consequences[]`、`articleRefs[]`、`reviewedAt`、`approvalId`；每个实质性要点也有引用，不只在卡片末尾堆条号 |
| `cards.json` | `id`、`revision`、`primaryLawId`、`topicIds[]`、`title`、`conclusion`、`story`、`interpretationIds[]`、`articleRefs[]`、`sourceIds[]`、`quizIds[]`、`reviewedAt`、`approvalId` |
| `questions.json` | `id`、`revision`、`kind`、`prompt`、`options[]`（稳定 option ID）、`correctOptionIds[]`、`explanation`、`cardIds[]`、`articleRefs[]`、`reviewedAt`、`approvalId`；V1 只做判断/单选，正确选项恰好一个 |
| `topics.json` | `id`、`parentId?`、`lawId`、`title`、`order`、`requiredForV1`；主题无环；★ 主题必须有已发布卡 |
| `courses.json` | `rulesVersion`、四档 `ranks[]`、有序 `levels[]`；关卡含 `id`、`rankId`、`prerequisiteIds[]`、`cardIds[]`、`questionIds[]`、`passRatio`；先修图无环且关卡非空 |
| `aliases.json` | 经审核的法律别名、拼音/首字母词典、主题关键词；不宣称任意自由问题都能匹配 |
| `search-index.json` | `indexVersion`、`packageId`、`sourceDigest`、分词规则版本、倒排记录；完全由发布包派生，不能成为原文事实源 |
| `migrations.json` | 旧 ID/引用 → 新 ID/引用的显式映射及原因；标注 `same`/`revised`/`removed`；拆分/合并不得擅自选一个目标 |

`conclusion` 包括 `category`（`unlawful` / `possibly_unlawful` / `attention`）、审核后的短文案及必要限定条件；不能由客户端根据关键词推断违法性。

`story` 为带类型结构：`official_case_adaptation` 必须有官方案例来源，保留原裁判事实及改编说明；`illustrative_scenario` 必须显著标注“典型情境示例”，只解释审核后的规则，不伪称真实案件、不编造裁判结果。该区别用于落实 PRD 的“典型情境”描述和案例改编红线。

`consequences` 使用 `{ quote, articleRef, location? }` 引用结构，处罚种类、幅度原样显示；`quote` 必须能逐字定位到引用文本。摘要、处罚图示及分享卡不可产生第二套手写处罚数值。

法条中的废止/删除条、增补条和特殊层级按官方文本完整保留。全文完整性用经双人确认的条目清单及有序摘要验证，不能假定“1 到 N 连续”就算完整。

### 4.3 审核状态与构建门禁

开发侧状态为 `draft → source_verified → reviewed → approved → released`；退回需记录原因。法条双人逐字校对、解读/案例专业审核及律师抽检均记录人员标识、角色、时间、审核对象摘要和结论。改变已审核对象后，旧签审不再适用。

发布必须同时满足：

1. schema、ID 唯一性、枚举、日期、UTF-8、文件路径和摘要检查通过。
2. 三法全量条目与经审核官方清单一致；原文差异报告逐项确认；不能只校验条数。
3. 每条引用命中精确 edition 和条号；解读↔卡片↔题目↔法条的前向/反向关系一致；处罚引文是原文的精确片段。
4. 所有内容有有效来源和对应摘要的签审记录；双人校对不能由同一个人填两个身份。律师抽检范围、风险项、未抽检项及包级放行结论保留在审核记录，不能把机器校验冒充人工签名。
5. 正式包没有草稿、测试条文、占位来源、缺少审批的卡或题；满足数量、题型、主题和关卡约束。
6. 超过 6 个自然月未复核的内容生成告警；发布门禁要求完成复核，或由内容负责人记录例外原因、影响及批准后才可放行。已知法改导致错误、来源不明或未签审不得例外放行。
7. 工具输出可定位的文件、ID、字段和原因；有错误返回非零。同输入重复生成的内容/索引字节一致；时间字段由发布输入给定，不随工具运行随机变化。

自动门禁证明结构和一致性，不证明法律判断正确。机器验证失败或专业审核未完成时，只能在隔离的开发测试目标使用明确标注的合成 fixture，不能进入正式 App Bundle。

## 5. 内容加载、升级和损坏恢复

### 5.1 启动顺序

`读取声明状态 → 必要时显示免责 → 校验 manifest/兼容性 → 后台打开内容与索引 → 初始化/迁移用户库 → 进入首页`。

首页内容可用状态与用户记录可写状态分别建模，不用一个 `isLoading` 混合表示所有错误。首页就绪前不开放错误版本的答题/检索入口。预生成索引、按需解码各法律/卡片集合，避免首启同步全库导入 SwiftData。

### 5.2 内容更新

- 新内容只能随新版 App 打包；冷启动读取当前 Bundle 的 `packageId`，不存在后台自动下载旧/新包。
- 新包校验后，在用户库事务中更新内容关联与激活记录；完成前不标记迁移成功。应用中断后可从未完成状态重试，不能重复累计进度。
- 法条收藏保存精确 `ArticleRef`。新 edition 不静默替换旧原文；有已审核映射时展示“内容已更新”及跳转，无法保留旧文本时只显示原收藏摘要和状态，不重建未打包的原文。
- 卡片/题目稳定 ID 可维持收藏关系，但 revision 变化需提示复核；题目历史保留当时的选项 ID、正确性与内容版本。改题后待复习状态重新计算，旧成绩不伪装成新版掌握程度。
- 删除/拆分内容保留收藏及历史占位，给出更新说明或让用户选择新目标。不得凭相同条号跨法律/跨版本匹配。

### 5.3 失败策略

| 故障 | 行为 |
|---|---|
| 核心内容摘要不符、缺法、引用破损、schema 不支持 | 阻断受影响内容；显示可复制内容包 ID 的错误页；不展示猜测文本 |
| 派生搜索索引缺失/损坏 | 从已验证 JSON 在后台重建可写缓存；期间保留分类及条号查询并提示搜索准备中 |
| 用户库初始化/迁移失败 | 保留原库，提供内容只读访问和重试；不自动删库重建，用户明确选择重置时才清除 |
| 磁盘不足/保存失败 | 保留当前答题上下文，显示“尚未保存”，允许重试；不宣称已打卡或已收藏 |
| 有新法律修订但当前安装包仍旧 | 保留真实版本与复核日期；App 不承诺离线实时现行性，运营侧必须启动发版审核 |

用户库演进从第一版建立 `VersionedSchema` 和迁移计划；每次升级在旧库副本上验证全部支持版本路径，成功前不覆写唯一原件。内容格式版本、法律版本、内容包版本、用户库 schema 版本分别管理。

## 6. 本地用户数据与确定性行为

### 6.1 存储契约

| 对象 | 主键/关键字段 | 不变量 |
|---|---|---|
| `Acknowledgement` | `disclaimerVersion`、`acceptedAt` | 同版本不重复要求知悉；不附带其他授权 |
| `Bookmark` | `targetType + targetIdentity`、`createdAt`、`status` | 法条/卡片类型明确，重复点击不产生重复记录 |
| `CardProgress` | `cardId`、`revision`、`startedAt`、`completedAt?` | 不靠滚动比例猜测已理解；完成动作可验证 |
| `PracticeSession` | `sessionId`、`mode`、`rulesVersion`、`packageId`、题目队列、位置、状态 | 创建时固定题目和版本；恢复不重新抽题 |
| `AnswerAttempt` | `attemptId`、`sessionId`、`questionId/revision`、`selectedOptionId`、`isCorrect`、`answeredAt`、`localDay`、`timeZoneId` | `attemptId` 幂等；保存答案与进度在同一提交边界 |
| `WrongQuestion` | `questionId + revision`、`lastWrongAt`、`wrongCount`、`reviewState` | 历史可查，复习答对不删除答题记录 |
| `LevelProgress` | `levelId`、`rulesVersion`、最好成绩、通关时间 | 重复结算不重复升级；规则变化显式迁移 |
| `DailyAssignment` | `localDay`、`questionId/revision`、`packageId` | 一日唯一；答题结果由 attempt 关联 |
| `StudyDay` | `localDay`、首次有效学习事件时间及时区 | 一天最多计一次；用于派生连续天数 |
| `Preferences` | 字号倍率、语速、提醒开关/时间、学习历史开关 | 业务设置与系统通知授权状态分开 |

复合唯一键在 iOS 17 采用一个规范化稳定 key 表达；不能直接使用需要更高系统版本的宏。首次发布前验证该编码无碰撞。记录引用内容 ID，展示时从只读内容层解析，避免把法条全文散落在用户表中。

### 6.2 实现默认值：完成、称号与错题

- 阅读知识卡后，完成其小测验并查看解析，点击“完成学习”才算完成该卡；答错也可完成阅读，但进入错题本。只打开详情不算完成。
- 有效学习事件是完成知识卡或提交有效答案；浏览首页、收到通知不算打卡。同一天只记一次；当天未学习时显示截至昨天的连续天数，不提前清零。
- 四档称号由已通过关卡决定，不是法律专业能力认证。课程包决定每档关卡及先修关系；默认每关 10 题、正确率达到 80% 通关（判断采用整数比较），最高称号要求所有对应先修关完成。数量不足的关卡在构建时拒绝。
- 答题状态：`unanswered → selected → submitted → explanation → next/finished`。选择可改，提交后锁定；重复点击提交返回同一次结果；必须展示解析才能继续。
- 错题默认进入“待复习”；在错题复习模式答对一次转“已复习”，再次答错转回“待复习”。保留错题历史筛选，不制造“永久掌握”的承诺。
- 默认仅本地保存必要学习记录；关闭学习历史后停止新增阅读历史/StudyDay，不上传任何信息。收藏、错题、关卡仍保存功能所需数据；界面解释范围并提供单独清理操作，清除需用户确认。

这些阈值属于产品实现默认值，必须在单一规则定义处实现，不能分别写在首页、练习页和称号页。

### 6.3 每日一题、时区与通知

- 按当前设备时区的公历日生成 `LocalDay`；首次分配后持久化。系统时间回拨或时区切换遇到已有日期键时复用，不重复获益；历史按记录时的日期保存，不回算。
- 在已审核题目 ID 的稳定有序列表上，用明确版本的稳定摘要算法计算每日偏移；禁止使用进程随机种子的语言默认 `hash`。测试注入时钟和固定题库。
- 本地预生成未来 30 日题目队列（实现默认值），启动、进入前台、日期/时区变化、内容升级时幂等补齐。已回答的日期保留历史；未回答题被撤下时显式标注更新后重新分配。
- 提醒默认关闭，用户主动开启才请求系统通知权限。使用每日重复的本地提醒，文案为通用“来答今日一题”，点击时路由到当天分配题，不在通知中固化易过期法律结论。
- 题目队列与通知调度分离；长期不打开 App 不依赖后台任务保持运行。重开 App 及时补齐队列；提醒由系统调度，不能承诺绕过静音、专注或系统设置准点触达。
- 开关/时间更改只替换本 App 的提醒标识；拒绝权限显示状态及系统设置入口。无网络、无通知权限均能答题。

## 7. 搜索与内容展示规则

### 7.1 搜索

1. 输入做查询侧归一化：去首尾空白、全半角、大小写、可识别条号和中文数字转换；原文存储和复制内容不进行同样改写。
2. 解析法律别名 + 条号（含“之一”等）。指定法律时直达匹配条；仅输入条号时列出三法匹配结果；不存在则明确提示，不跳相近条冒充匹配。
3. 关键词按法律/主题可筛选；构建索引使用中文字符组合及经审核词典。字符组合候选需对归一化正文再做短语验证，避免只有分散字符也命中。
4. 拼音联想只基于内置词典的全拼、首字母和前缀；同音/多音词人工维护，不在线调用输入法服务。
5. 默认排序：明确法条命中 → 标题/主题精确匹配 → 正文短语匹配 → 关键词候选；同分以法律固定顺序及条文顺序稳定排序。
6. 展示结果类型、法律名、条号/标题、版本及高亮片段；选择才加载全文。查询长度上限实现默认值 100 字，超出给出提示，不静默截断到错误查询。
7. 空输入展示法律目录和内置检索提示；零结果提供换词/按条号浏览入口，不生成答案。

### 7.2 页面与交互

默认五个 Tab：首页、学法堂、查法条、练习场、我的。首页是入口聚合，各功能页保持自己的筛选和返回位置。

- 知识卡顺序：场景标题 → 有限定条件的结论徽章 → 300 字内故事 → 白话要点 → 可展开原文 → 常见误区 → 小测验 → 来源、更新月份、免责、纠错。每条引用点击跳至完整法条详情并保留返回位置。
- 法条详情：法律名称、条号、施行版本与复核日期置顶；完整原文、复制/收藏/朗读、关联解读和卡片。无关联卡可正常展示原文，不能生成填充解读。
- 复制原文不裁剪、不改标点；附加来源与版本时用独立区段，与法条文本区分。分享引文从原文选择完整段落，不用省略号隐藏处罚条件；过长时分页图片，不能裁掉来源/免责。
- 题目解释页无论对错均显示关联卡与法条入口；答错时自动展开相关原文。不用动效替代文字反馈。
- 所有内容详情及答题解析复用同一免责声明组件，固定文案来自 PRD：

> 本 App 内容仅为法律知识普及，不构成法律意见。具体法律问题请咨询执业律师或前往法律援助机构（12348 热线）。

“固定”指文案与出现位置一致，不要求悬浮遮挡正文。首次启动展示完整声明并提供显式勾选；来源、适用范围、版本时效及纠错说明作为完整页的一部分。

### 7.3 视觉与无障碍

- 主色竹青绿 `#3A9D6E`、暖米白 `#FBFBF7`、法条墨色 `#1F2937`；语义颜色分别定义浅/深色资源，结论三态同时显示文字/符号，不能只靠颜色判断。
- 系统字体 + Dynamic Type；标准正文不小于 17pt，法条原文高一档。PRD 的 1.6 行距按实际行高效果验收，不把 SwiftUI `lineSpacing(1.6)` 当作 1.6 倍行高。
- 圆角 16–20pt，常规触控区至少 44×44pt；浅/深色对比度、超大字号、横屏及 iPad 分屏分别检查。
- 字号设置为相对系统字号的有限倍率，不截断法条或限制辅助功能字号；大字号下按钮允许换行，卡片不设固定文本高度。
- VoiceOver 顺序与阅读顺序一致，正确/错误、版本、收藏状态有可读标签；尊重减少动态效果，不依靠颜色或动画传达结果。
- 朗读可选择原文或解读，读前说明内容类型。一次只允许一个朗读会话；页面退出、音频中断及新会话替换的停止行为明确。语速持久化并映射到系统允许范围。
- 只使用设备可用的系统语音；首次离线无合适语音时提示并允许继续阅读，不自动下载、不假装已朗读。不做后台持续播放承诺。

## 8. 隐私、反馈与发布资料

- 不请求联系人、定位、相册全库、麦克风等无关权限。生成分享图使用临时文件及系统分享；不因分享默认申请照片权限。

- 反馈邮箱、支持页、隐私政策页、个人开发者签名 Team、Bundle ID、商标检索结果、内容审核责任人是发布前待落实信息，禁止用虚构值完成发布配置。

## 9. 工程工作流：Skill 与独立 Worktree

### 9.1 每个新需求独立开发

新功能、缺陷修复、内容升版和实质文档需求均使用独立分支及 worktree；同一需求的连续修订可留在原 worktree。禁止直接在 `main` 开发，禁止把不同需求混到同一工作树。

开始前读取 `Agents.md`、本文及对应目录规则，检查 `git status --short` 和 `git worktree list`。未提交的用户改动必须保留。示例（在主仓库根目录执行，基线应为已确认的当前主线）：

```sh
git status --short
git worktree list
git worktree add -b codex/<requirement-id>-<slug> ../LearnLaw-<requirement-id> main
cd ../LearnLaw-<requirement-id>
```

worktree 默认放仓库外；若环境限制则使用已忽略的专用位置，不嵌套提交。先完成本需求的 spec/验收切片，再按 §9.3 实现。每个 worktree 使用独立构建输出、测试库和临时内容产物，不共享可变生成目录。

结束时提交小而完整的变更，写明原因、结果、验证；涉及内容/架构的变更同步文档及图。合并前查看当前主线和差异，执行必要检查，不能覆盖其他改动。按仓库协作约定提交审查/整合；无明确发布要求时不因 skill 的通用推送建议擅自向远端主线发布。

清理仅在确认已整合/已备份、没有未提交文件、没有其他会话使用后执行：

```sh
git worktree remove ../LearnLaw-<requirement-id>
git branch -d codex/<requirement-id>-<slug>
```

不用 `--force` 删除未提交工作，不用强推或重置主线作为普通收尾手段。新需求不得复用已完成需求的分支。

### 9.2 必须使用相关 Skill

实现前按任务读取对应 `SKILL.md`，在任务记录写明采用的 skill 及验证方式。不要只记录名称而不读取内容；使用者指令和本项目 iOS 17/产品边界优先于 skill 通用示例。

| 工作 | 必须/按需使用的 skill |
|---|---|
| 所有代码变更、测试与重构 | **ub-mode** |
| 架构图新建/修改 | **archify**，保留输入 JSON、生成 HTML 和自动检查凭据 |
| iOS 架构及页面 | `swift-architecture`、`swiftui-patterns`；导航用 `swiftui-navigation`，布局用 `swiftui-layout-components` |
| iOS 数据/并发/解码 | `swiftdata`、`swift-concurrency`、`swift-codable`，按变更涉及能力选择 |
| iOS 测试/设备验证 | `swift-testing`、`ios-simulator`；性能问题用 `swiftui-performance`/`debugging-instruments` |
| iOS 无障碍/通知/系统桥接 | `ios-accessibility`、`push-notifications`、`swiftui-uikit-interop`，按任务使用；TTS 另核查 AVSpeechSynthesizer 官方 API |
| Android 启动与质量 | `android-cli`、`testing-setup`；先完成 Android 技术决策，再使用选定技术对应 skill |
| Android Compose/导航/适配 | 选用 Compose 时读取 `adaptive`、`edge-to-edge`、`navigation-3`；性能任务读取 `jetpack-compose-performance` |
| Android 权限/发布审核 | 涉及时读取 `android-permissions-security`、`android-intent-security`、`play-policy-insights` |
| 图像生成/修改 | 涉及时使用 `imagegen`，原始素材和授权记录进入 `resource/` |

skill 不可用时先寻找当前安装路径；必要 skill 确实缺失时说明缺口，不声称已遵循。框架 API 和权限规则按实现当时的官方资料核查。新系统 API 必须有可用性判断与低版本实现；不得为了照搬示例抬高最低系统版本。

### 9.3 ub-mode 落地规则

1. **First Make it Work**：先确定领域数据形状及可检查结果；最小纵向切片跑通。一个决策只有一个定义位置。
2. 行为变更先写能暴露问题的测试，看到预期失败，再做最小修复；纯文档/素材调整不写与实现同构的无效测试，采用链接、格式或产物验证。
3. 输入边界校验一次，内部使用可信类型；业务规则用纯函数。非法状态由类型/约束排除，禁止用强制解包和吞错掩盖损坏。
4. 不需要共享的状态隔离；必须共享时只有一个写入者。导入、迁移、调度、提交答案应能幂等重试。
5. **Then Make it Right**：按可验证小单元重构，修原因；先减复杂度再加抽象，测试用户能观察到的行为。
6. 两种修复因同一前提连续失败时，记录该前提及状态所有权，先纠正设计，再进行下一轮修复。
7. 按 skill 使用 crapper/dryer/mutator 等质量工具；项目未接入或平台不支持时记录“未运行”和原因，采用行为测试、复杂度及重复代码审查作为临时证据，不编造通过结果。首次接入评估与使用放在有代码的需求内。
8. **Follow Practice**：需求记录写明每项主要操作、原因、验证结果和遗留限制；小步提交；确认 worktree 不再使用后清理。

### 9.4 完成定义（DoD）

需求说明、实现及验收条件一致；相关 skill 已读取；有独立 worktree/分支；必要行为测试和平台构建通过；跨引用/数据迁移/权限失败路径已验证；内容无未审事实；文档、架构图和操作记录同步；没有密钥/缓存/测试数据混入发布包。不能用“能编译”代替内容审核或用户流程验收。

## 10. 验证计划与非功能验收

### 10.1 必需测试集合

| 层级 | 代表性场景 | 通过条件 |
|---|---|---|
| 内容工具 | 缺引用、错误 edition、缺条、篡改引文、重复 ID、未签审、旧签名、草稿混入、未来/过期复核日期 | 均给可定位错误；合法包可确定性重建 |
| 领域规则 | 60%/80%/100% 判分、锁定答案、重复提交、日历跨月跨年/闰日/时区/回拨、同日分配、先修关卡 | 输入固定输出确定；无重复进度/打卡 |
| 内容检索 | 中文、拼音、首字母、全半角、同条号跨法、增补条、零结果、快速改词、长输入 | 查询正确且稳定；原文不被归一化改写 |
| 持久化 | 收藏去重、进程重启、保存失败、旧 schema 升级、内容删除/改题/拆分、迁移中断重试 | 原始记录保留，不错配或静默重置 |
| 系统适配器 | 通知拒绝/撤回、修改时间、无语音、朗读中断、无邮件客户端、取消分享 | 可恢复，核心离线功能不受阻 |
| UI 关键链路 | 首启→选主题→读卡→展开法条→答错→复习→收藏→重启 | 状态及引用闭环；显示来源、版本、免责声明 |
| 可访问性/适配 | 深浅色、VoiceOver、最大 Dynamic Type、减少动画、iPhone 小/大屏、iPad 横屏/分屏 | 正文完整、控件可操作、焦点顺序正确 |
| 离线与隐私 | 飞行模式全链路；网络请求观察；包及权限审查 | 核心功能无外部请求；分享/邮件只由用户主动触发 |

iOS 单元测试采用项目锁定工具链可用的 Swift Testing；UI/性能验收使用 XCTest/XCUITest 等合适能力。每次改动只运行与风险相关的必要检查，通过后不无理由重复全量测试。正式发版执行全量验收。

### 10.2 性能和体积口径

| 指标 | 门槛与测法 |
|---|---|
| 冷启动 | ≤2s：Release 构建、最低支持真机档位（默认以 iPhone SE 第 2 代为基准，若不可用需记录等价替代）、飞行模式；从进程启动到首屏可交互且必需数据就绪。首装和已有用户库分别测 ≥20 次，记录 P50/P95，以 P95 验收；用户阅读免责时间不计 |
| 检索 | ≤200ms：正式全量包、预生成索引；从触发查询到首批可用结果，记录 ≥100 组混合查询的 P95；输入 debounce（默认 150ms）另计并报告整体体感耗时 |
| 内容体积 | 法条+内容 JSON+索引+随包审核摘要合计 ≤15MB；同时记录压缩和解压尺寸，门槛以实际未压缩 Bundle 内容为准 |
| App 体积 | 目标 ≤30MB：记录 Release 归档后的设备适配下载大小及安装大小，不用源码目录或模拟器包大小代替；超标须列出归因和处理结论 |
| 主线程 | 解析、索引构建和批量迁移不在交互主线程执行；性能分析提供卡顿路径证据 |

性能基准采用真实发布量数据，不能拿 5 张示例卡的结果宣称达标。设备/OS/工具链、样本规模、构建配置和测量脚本随报告保存。
