## 主要发现（按优先级）

### R1 · P1 · 缺少 Required Reason API 隐私清单

[AppModel.swift](../../ios/LawSense/App/AppModel.swift) 的 `Preferences`（第 42–65 行）使用 `UserDefaults` 保存字号、语速和免责状态，但源码及两个已构建 App Bundle 均无 `PrivacyInfo.xcprivacy`；[工程生成器](../../ios/Scripts/generate_project.py) 第 66–67 行也没有打包该资源。

这不代表偏好保存方式本身不安全；问题是发布隐私声明缺失。Apple 将 `UserDefaults` 列为需要申明使用理由的 API；当前仅访问自身偏好数据的用途应核对 `NSPrivacyAccessedAPICategoryUserDefaults` / `CA92.1`，并将 manifest 加入每个使用该 API 的应用 target，再验证最终归档。依据：[Apple Required Reason API](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype)、[Apple Upcoming Requirements](https://developer.apple.com/news/upcoming-requirements/)，核查日期 2026-10-31。

设置页只有简短离线隐私说明，还没有可访问的正式隐私政策链接及完整的保留/删除说明。上架前需与 App Store Connect 填报一致；本次没有访问 App Store Connect，不能声称已核实其后台配置。依据：[App Review Guidelines 5.1.1](https://developer.apple.com/app-store/review/guidelines/#data-collection-and-storage)。

### R2 · P2 · 设备时间回拨会错误改变错题状态（实测复现）

[UserStore.swift](../../ios/LawSense/Data/UserStore.swift) 第 146–155 行按最大的 `Date` 判断最近一次答错/复习，等同于假定设备时间一直向前。实际用户操作顺序与这个假定不一致时：

1. 先答错，将系统时间往回调，再复习答对：仍被列为待复习。
2. 先答错并复习答对，将时间往回调后再次答错：错误地保持已复习。

新增 [AuditRegressionTests.swift](../../ios/LawSenseTests/AuditRegressionTests.swift) 直接调用未修改的 `UserStore`，两个用例均失败，命中上述两种行为。这是现有测试未覆盖的正确性问题，不能用高行覆盖率抵消。

建议：由单一写入者持久化事件提交顺序，按提交顺序推导复习状态，保留墙钟时间用于显示/日期。不能仅用进程内单调时钟作为跨重启序号。修复后必须让这两个回归测试转绿，并覆盖重启、相同时间戳和新的答错事件。

### R3 · P2 · 用户库故障仍会阻断全部内容阅读（计划内缺口）

[AppModel.swift](../../ios/LawSense/App/AppModel.swift) 第 18–28 行把用户库打开异常放入整体加载错误；[LawSenseApp.swift](../../ios/LawSense/App/LawSenseApp.swift) 第 25–34 行只有 catalog 和 user 同时存在才开放主界面。用户库打不开时，即使 Bundle 内容完整也只剩错误页和重试。

开发 spec §5.3 要求保留原库并提供内容只读访问。D04 交付记录已明确将此项后置，但它仍是完整 MVP 的未完成项。当前未做磁盘不足、损坏数据库和迁移失败的故障注入测试，不能声称这些路径安全可恢复。

## 性能

以下是源码证据支持的规模风险，**不是已测出的卡顿或已证明超标**：

- `UserStore` 整体位于 MainActor，第 164–171 行在每次写入后重新读取/排序全部答题、收藏、完成记录；收藏和今日分配也先全表读取。记录增长会增加主线程 I/O 和分配。

## 测试与覆盖率

领域测试本次重新运行：10 个测试通过（其中两个为参数化测试）。LLVM 报告的 Domain 行覆盖率为 **91.52%（151/165）**；仅统计 Domain，不能当作整个 App 的覆盖率。各文件证据：[领域覆盖率摘要](ios-audit-domain-coverage.json)。

原有 4 项 SwiftData 测试重新通过，新增 2 项时间回拨回归测试失败。首轮 UI runner 在准备阶段崩溃，未执行 UI 用例；随后单独重跑 3 条 UI 流程全部通过（`audit-ui-retry.xcresult`）。因此既有 17 项测试本次均通过，但新增 2 项回归失败，不能判定全部测试要求满足。新增两个时间回拨回归测试保持正常断言，没有跳过或用 expected-failure 掩盖问题，审查分支测试应因此为红色；应用开发分支保持不变。

仅这 6 项 hosted 测试（含失败用例）的 xccov 数据：UserStore 行覆盖率 **98.54%**，但两个状态用例仍失败；App 合计 18.02%，因为该结果包中的 UI 未执行；后续 UI 单独重跑通过，这个 18.02% 仍不能当作合并后的 App 最终覆盖率。[hosted 覆盖率证据](ios-audit-hosted-coverage.json)。

关键缺口包括：内容文件缺失/摘要篡改/不支持 schema、保存失败与回滚、损坏库/迁移中断、免责升级与进程重启、跨日/时间回拨、通知/邮件/分享失败、TTS 生命周期及大字号无障碍。UI 测试目前启用内存用户库并重置测试偏好，不能证明进程重启持久性；文件库重开测试仅覆盖有限数据操作。

本次运行还出现 SQLite `vnode unlinked while in use` 日志，定位到 `UserStoreTests.swift` 的临时文件库清理：defer 删除目录时数据库句柄尚未完全释放。断言虽通过，但测试清理生命周期需要修正，或在隔离进程退出后再清理。这是测试环境问题，不把它当作生产用户库已损坏的证据。

未发现 CI workflow，也没有统一自动执行 Swift Package 测试 + Xcode 测试 + 发布包隔离检查的入口；当前需人工执行。`crapper` / `dryer` / `mutator` 未接入，未声称相应门禁通过。
